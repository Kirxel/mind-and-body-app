# AGENTS.md — «Разум и Тело»

## 1. Назначение проекта

Этот репозиторий содержит сайт организации «Разум и Тело».

Основные направления:
- массаж;
- работа с опорно-двигательным аппаратом;
- физиотерапевтические услуги;
- психотерапия;
- информационные материалы о специалистах, подходах и услугах;
- заявки / запись / обратная связь.

Основной стек:
- frontend: Next.js + TypeScript;
- backend: FastAPI + Python;
- backend I/O: async-first;
- CI/CD: GitHub Actions;
- deployment: контейнеризованный и воспроизводимый.

Предпочтительная структура монорепозитория:

```text
apps/
  web/        # Next.js + TypeScript
  api/        # FastAPI
infra/        # Docker, reverse proxy, deployment config
docs/         # ADR, API notes, content rules
.github/
  workflows/  # CI/CD
```

## 2. Главный принцип работы агентов

Не вносить крупные изменения без понимания контекста.

Перед реализацией:
1. изучить существующую структуру и связанные файлы;
2. определить влияние на frontend, backend, API-контракты, тесты и deployment;
3. для кросс-функциональной задачи сначала привлечь `teamlead`;
4. по возможности делегировать независимые части профильным агентам;
5. после реализации прогнать QA;
6. перед завершением значимой задачи провести review.

Роли:
- `teamlead` — архитектура, декомпозиция, координация, интеграционные решения;
- `frontend` — Next.js, TypeScript, UI, UX, SEO, accessibility;
- `backend` — FastAPI, async Python, API, БД, интеграции;
- `qa` — тест-план, автотесты, регрессии, проверка критериев приёмки;
- `reviewer` — независимый read-only review;
- `deploy` — Docker, GitHub, GitHub Actions, CI/CD, окружения и deployment.

## 3. Контент и медицинские формулировки — обязательное правило

Сайт НЕ должен обещать лечение, исцеление или гарантированный медицинский результат.

Запрещённые или нежелательные формулировки в маркетинговом и интерфейсном тексте:
- «лечим»;
- «вылечиваем»;
- «излечиваем»;
- «исцеляем»;
- «гарантируем выздоровление»;
- «избавим от заболевания»;
- любые аналогичные обещания гарантированного результата.

Не создавать утверждения вида:
- «наш массаж лечит ...»;
- «физиотерапия гарантированно устраняет ...»;
- «психотерапия вылечит ...»;
- «мы поставим диагноз ...», если конкретный функционал и квалификация специалистов этого явно не предусматривают.

Предпочтительные нейтральные формулировки:
- «работаем с ...»;
- «помогаем улучшить самочувствие»;
- «помогаем снизить выраженность дискомфорта»;
- «поддерживаем восстановление и функциональную активность»;
- «подбираем подход с учётом состояния и индивидуальных особенностей»;
- «проводим консультации»;
- «оказываем услуги по ...»;
- «может способствовать ...» — только когда это уместно и не превращается в гарантию результата.

Текст должен:
- быть спокойным, профессиональным и понятным;
- не запугивать пользователя;
- не обещать результат, который нельзя гарантировать;
- не подменять медицинскую консультацию рекламным текстом;
- не создавать ложного впечатления о квалификации специалиста.

Если формулировка вызывает сомнение, агент обязан выбрать более нейтральный вариант и отметить вопрос для контентного/юридического согласования.

## 4. Архитектурные правила

### Frontend

Использовать:
- Next.js с App Router;
- TypeScript в strict-режиме;
- Server Components по умолчанию, Client Components только при необходимости;
- семантическую HTML-разметку;
- доступность с клавиатуры;
- корректные metadata, Open Graph, sitemap/robots там, где это применимо;
- централизованный API client;
- runtime validation внешних данных там, где это оправдано;
- формы с понятными состояниями loading / success / error.

Не дублировать бизнес-правила backend на клиенте, кроме правил, необходимых для UX.

### Backend

Использовать:
- FastAPI;
- async endpoints;
- async DB driver и async session;
- неблокирующие клиенты для внешних HTTP/API вызовов;
- Pydantic-модели для входных/выходных данных;
- явный service/use-case слой для бизнес-логики;
- dependency injection FastAPI для зависимостей;
- миграции БД;
- структурированное логирование.

Не использовать блокирующий I/O внутри `async def`.
Если сторонняя библиотека синхронная и заменить её нельзя — изолировать вызов через threadpool и явно прокомментировать причину.

### API

- Версионировать публичный API, например `/api/v1`.
- Возвращать предсказуемые схемы ошибок.
- Не передавать stack traces клиенту.
- Не доверять данным frontend.
- Валидировать пользовательский ввод на backend.
- Не хранить секреты в репозитории.
- Для персональных/чувствительных данных собирать только необходимый минимум.

## 5. Качество кода

Обязательные свойства:
- небольшие, сфокусированные модули;
- понятные имена;
- отсутствие мёртвого кода;
- отсутствие `any` без обоснования;
- отсутствие необоснованных `# type: ignore`;
- явная обработка ошибок;
- тестируемая бизнес-логика;
- отсутствие секретов и персональных данных в логах;
- минимальное количество новых зависимостей.

Не добавлять production dependency, если задача решается стандартными средствами или уже установленной библиотекой.

## 6. Тестирование

Frontend:
- unit/component tests для значимой логики;
- E2E для критических пользовательских сценариев;
- проверка адаптивности и доступности для основных страниц.

Backend:
- unit tests для service/use-case слоя;
- API/integration tests;
- async tests для async-кода;
- негативные сценарии и validation errors.

Критические сценарии для сайта:
- просмотр услуг;
- просмотр карточек специалистов;
- отправка заявки/формы;
- ошибки формы;
- защита от некорректного ввода;
- корректная работа контактов и CTA;
- отсутствие запрещённых медицинских обещаний в пользовательском тексте.

## 7. Security и privacy

Всегда проверять:
- XSS и небезопасный HTML;
- CSRF там, где применимо;
- CORS;
- rate limiting для публичных форм/API;
- безопасную обработку файлов, если загрузка файлов будет добавлена;
- секреты только через environment/secrets;
- отсутствие секретов в клиентском bundle;
- отсутствие чувствительных данных в логах;
- безопасные cookie flags для auth/session;
- dependency vulnerabilities в CI.

Не разрабатывать собственную криптографию.

## 8. Git и изменения

Агенты не должны:
- force-push без явного запроса пользователя;
- удалять чужие изменения без необходимости;
- коммитить секреты;
- менять CI/CD или production-конфигурацию скрытно.

Каждое существенное изменение должно иметь:
- понятную цель;
- тест или аргумент, почему тест не нужен;
- описание возможных рисков;
- обновление документации при изменении поведения/API.

## 9. Definition of Done

Задача считается завершённой, когда:
- критерии приёмки выполнены;
- типы и lint проходят;
- тесты проходят;
- frontend и backend согласованы по контракту;
- новый текст не нарушает правила медицинских формулировок;
- нет очевидных security/privacy регрессий;
- reviewer не нашёл блокирующих замечаний;
- deployment impact учтён;
- документация обновлена, если изменились интерфейсы, окружение или эксплуатация.

## 10. Code Review Rules

Reviewer должен в первую очередь искать:
1. ошибки поведения и edge cases;
2. security/privacy проблемы;
3. async/blocking ошибки backend;
4. расхождения frontend/backend API;
5. отсутствие необходимых тестов;
6. accessibility и SEO регрессии;
7. медицинские/маркетинговые обещания, нарушающие раздел 3;
8. проблемы CI/CD, миграций и backward compatibility.

Не тратить основное внимание review на косметические замечания, которые автоматически ловятся formatter/linter.
